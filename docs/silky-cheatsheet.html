Silky 微服务框架

基于 .NET 平台的开源微服务开发框架，专注 RPC 通信与微服务治理两大核心能力。
核心理念：接口即服务 —— 一个标注了 [ServiceRoute] 的普通 C# 接口，就是一个完整的微服务端点。自动生成 HTTP WebAPI 与 RPC 端点，无需手写 Controller。

1框架概览

它解决什么

把普通 .NET 主机应用以最小侵入升级为微服务：自动获得服务注册发现、远程调用、负载均衡、熔断限流、分布式事务。

与同类框架的差异

不需要 Sidecar 进程（对比 Dapr），不需要 Protobuf 代码生成（对比 gRPC），不引入新编程范式。会接口、DI、中间件就够。

最小上手代码

await Host.CreateDefaultBuilder(args)
    .ConfigureSilkyGeneralHostDefaults()
    .Build().RunAsync();

横向对比

特性SilkyDaprMassTransitgRPC
开发语言C# / .NET多语言C# / .NET多语言
RPC 方式接口代理·透明HTTP/gRPC Sidecar消息总线Protobuf 代码生成
服务治理内置完整内置（Sidecar）部分需自行实现不支持
分布式事务TCC 内置SagaSaga / Outbox不支持

最小可运行示例

① 契约层（独立项目，供其他服务引用）

[ServiceRoute]
public interface IGreetingAppService
{
    Task<string> Say(string line);
}

② 实现层

public class GreetingAppService : IGreetingAppService
{
    public Task<string> Say(string line)
        => Task.FromResult($"Hello {line}");
}

就这样 —— 自动变成可被 RPC 调用、可被网关暴露为 GET /api/greeting/say 的微服务。

③ 网关 Startup

public void ConfigureServices(IServiceCollection services)
{
    services.AddSilkyHttpCore()
        .AddSwaggerDocuments()
        .AddRouting()
        .AddDashboard();
}

public void Configure(IApplicationBuilder app, ...)
{
    app.UseDashboard();
    app.UseRouting();
    app.UseWebSockets();
    app.UseSilkyWebSocketsProxy();
    app.UseSilkyHttpServer();
    app.UseEndpoints(e => e.MapSilkyRpcServices());
}
脚手架：dotnet new --install Silky.App.Template → dotnet new silky.app -n MyApp，一键生成含 Docker Compose、Apollo、SkyWalking 的生产级骨架。

5RPC 调用：像本地方法一样

调用方只引用契约层，注入接口即可。底层由 Autofac 动态代理接管，调用体验与本地方法完全一致。

public class OrderAppService : IOrderAppService
{
    private readonly IGreetingAppService _greeting;
    private readonly IProductAppService _product;

    public OrderAppService(IGreetingAppService greeting,
                             IProductAppService product)
    { _greeting = greeting; _product = product; }

    public async Task<string> CreateAsync(string name)
        => await _greeting.Say(name);  // 透明 RPC
}

代理内部串起的完整链路

缓存拦截

命中缓存直接返回，不发网络请求

熔断 / 限流

Polly 熔断保护、实例级并发控制

负载均衡

轮询 / 随机 / 哈希一致性，剔除不健康实例

RPC 调用

DotNetty TCP 长连接

故障转移 / 降级

异常重试其他实例，最终走 Fallback

RpcContext：隐式传参

基于 AsyncLocal 的 RPC 上下文，服务间透传数据，不污染方法签名。TCC 事务里经常用到。

// 生产者
RpcContext.Context.SetInvokeAttachment("orderId", order.Id.ToString());

// 消费者
var orderId = RpcContext.Context.GetInvokeAttachment("orderId");

// 连接信息（客户端/服务端 Host、Port、协议）
RpcContext.Context.Connection;

② 方法级覆盖：[Governance]

// 禁止外网访问，只允许集群内部 RPC 调用
[Governance(ProhibitExtranet = true)]
Task<GetProductOutput> DeductStock(DeductStockInput input);

// 覆盖负载均衡与超时
[Governance(ShuntStrategy = ShuntStrategy.HashAlgorithm, TimeoutMillSeconds = 10000)]

实践建议 像"扣减库存""扣减余额"这类内部方法，都应该加 ProhibitExtranet = true。

③ 服务降级

[Fallback(typeof(IProductAppService), MethodName = "GetFallback")]
Task<GetProductOutput> Get(long id);

④ 缓存拦截（性能杀手锏）

命中缓存直接返回，根本不发网络请求。三个特性：

读 Get

[GetCachingIntercept(
  "Account:Id:{id}",
  OnlyCurrentUserData=true)]

写 Update

[UpdateCachingIntercept(
  "Account:Id:{Id}")]

删 Remove

[RemoveCachingIntercept(
  "GetAccountOutput",
  "Account:Id:{id}")]
  • Key 模板支持 {参数名} 占位，也支持 {0} 序号
  • OnlyCurrentUserData：按当前用户隔离缓存（避免用户数据串号）
  • IgnoreMultiTenancy：忽略多租户维度
  • 启用 Redis 后端：引入 Silky.Caching.StackExchangeRedis + DistributedCache:Redis:IsEnabled = true

7TCC 分布式事务

内置 TCC（Try-Confirm-Cancel），通过 AOP 拦截器 + Redis 事务日志保证最终一致性。接口标注 [Transaction]，实现标注 [TccTransaction]。

Try

预留资源，透传业务 ID 给后续阶段

Confirm

全部成功 → 推进到终态

Cancel

任一失败 → 回滚补偿

契约层

[ServiceRoute]
public interface IOrderAppService
{
    [Transaction]
    Task<GetOrderOutput> Create(CreateOrderInput input);
}

实现层

[TccTransaction(ConfirmMethod = "OrderCreateConfirm",
                CancelMethod  = "OrderCreateCancel")]
[UnitOfWork]
public async Task<GetOrderOutput> Create(CreateOrderInput input)
    => await _orderDomainService.Create(input);

[UnitOfWork]
public async Task<GetOrderOutput> OrderCreateConfirm(CreateOrderInput input)
{
    var orderId = RpcContext.Context.GetInvokeAttachment("orderId");
    var order = await _orderDomainService.GetById(orderId.To<long>());
    order.Status = OrderStatus.Payed;   // 推进终态
    return (await _orderDomainService.Update(order)).Adapt<GetOrderOutput>();
}

[UnitOfWork]
public async Task OrderCreateCancel(CreateOrderInput input)
{
    var orderId = RpcContext.Context.GetInvokeAttachment("orderId");
    if (orderId != null)   // 空回滚防护
    {
        var order = await _orderDomainService.GetById(orderId.To<long>());
        order.Status = OrderStatus.UnPay;
        await _orderDomainService.Update(order);
    }
}

必须遵守的规则

  • ① 幂等
    Confirm / Cancel 必须幂等 —— 网络抖动会重试
  • ② 空回滚
    Try 未执行就收到 Cancel，需判空处理（见左侧 orderId != null）
  • ③ 防悬挂
    Cancel 先于 Try 到达的情况
  • ④ 签名一致
    Confirm / Cancel 的方法参数必须与 Try 完全一致
  • ⑤ 自动恢复
    定时任务恢复悬挂事务：ScheduledRecoveryDelay 默认 30s，RetryMax 10 次
Try 阶段通过 RpcContext 透传业务 ID（示例中的 orderId），Confirm / Cancel 才能拿到正确的记录。这是官方 sample 的标准写法。

9特性速查

路由

[ServiceRoute]默认模板 api/{appservice}
[ServiceRoute(template: "api/order/{appservice}")]自定义路由模板
[ServiceRoute(ServiceName = "order")]显式指定服务名
[HttpGet("{id:long}")] [HttpPost] [HttpPut] [HttpDelete("{id}")]指定 HTTP 方法与子路径

鉴权

[Authorize]接口级，要求认证
[AllowAnonymous]方法级，匿名放行（如登录接口）

治理

[Governance(ProhibitExtranet = true)]禁止外网访问，仅集群内 RPC 可调
[Governance(ShuntStrategy = ShuntStrategy.HashAlgorithm, …)]方法级覆盖负载均衡 / 超时 / 熔断 / 重试
[Fallback(typeof(IXxxAppService), MethodName = "Xxx")]RPC 失败时执行降级方法

缓存拦截

[GetCachingIntercept("key:{id}", OnlyCurrentUserData = true)]读：命中直接返回
[UpdateCachingIntercept("key:{Id}")]写：更新缓存（AllowMultiple = true）
[RemoveCachingIntercept("CacheName", "key:{id}")]删：失效缓存，需指定 cacheName 或 Type

事务

[Transaction]标注在接口方法上，声明参与分布式事务
[TccTransaction(ConfirmMethod = "…", CancelMethod = "…")]标注在实现方法上，指定 Confirm / Cancel
[UnitOfWork]工作单元，配合 EF Core 使用

  └── Orders/IOrderAppService.cs

黄金法则：契约层（Application.Contracts）必须独立成项目。调用方只引用契约、不引用实现 —— 这是 Silky 透明 RPC 能成立的前提，也是避免服务间隐式耦合的关键。

12踩坑清单

坑说明
RPC Token 必填rpc:token 不允许为空，且集群内所有服务必须一致，否则连不上
